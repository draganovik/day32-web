# Day32

Day32 is a focused, provider-connected calendar manager. Version 2 is a static
Vue 3 application that connects directly to Google Calendar with Google Identity
Services. It has no Day32 user account or backend: the connected calendar account
is the session.

The UI and stores depend on provider-neutral calendar contracts. Google-specific
OAuth and Calendar API behavior lives in an adapter so Microsoft Outlook and
multiple concurrent connections can be added later.

Developer: [mladen.dev](https://mladen.dev)

## Stack

- Vue 3 with Composition API and typed `<script setup>`
- TypeScript
- Vite
- Tailwind CSS 4 through the official Vite plugin
- Pinia
- Vue Router
- Lucide icons for Vue
- Google Identity Services and Google Calendar REST API
- A versioned first-party service worker generated by a typed Vite plugin
- Vitest, ESLint, and Prettier

## Local development

Use Node 24 (see `.nvmrc`), then:

```sh
npm install
cp .env.example .env.local
npm run dev
```

Set `VITE_GOOGLE_CLIENT_ID` in `.env.local` to a Google OAuth 2.0 Web
application client ID.

The Google Cloud project must have:

1. Google Calendar API enabled.
2. An OAuth consent screen configured for the intended audience.
3. Local and production origins added to **Authorized JavaScript origins**:
   `http://localhost:5173` and the production origin.
4. The requested Calendar, OpenID, email, and profile scopes approved or added
   as test scopes while the app remains in testing.

The client ID is public browser configuration, not a secret. Restrict it to the
expected origins and APIs.

## Token and persistence model

- Google access tokens exist only inside the active adapter instance in memory.
- Closing or reloading the tab requires reconnecting.
- Disconnecting revokes the active Google token.
- Only UI preferences are persisted to `localStorage`.
- Calendar events, account profiles, and provider tokens are not persisted.
- The service worker caches the application shell and static assets, never
  Calendar or OAuth responses.

This is the safest useful model for a static application. Durable sessions,
background synchronization, and refresh tokens require a backend.

## Deployment

The project is configured as a Vercel static Vite application in `vercel.json`.
Set `VITE_GOOGLE_CLIENT_ID` for Preview and Production in Vercel, deploy, then
add the final deployment origins in Google Cloud Console.

The former generated GitHub Pages `docs/` build has been removed. Build output
is generated into `dist/` and should not be committed.

See [docs/provider-roadmap.md](docs/provider-roadmap.md) for the future
multi-account and Outlook plan.
